# Internationalisation du front (FR / EN / NL)

Le site était intégralement écrit en français, en dur, dans neuf pages HTML et
une douzaine de modules JS. Il parle désormais **français (référence), anglais
et néerlandais de Belgique**, avec une seule copie de chaque page.

---

## 1. Architecture

**Dictionnaires JSON + hydratation du DOM au runtime.** Pas de pages dupliquées
par langue, pas d'étape de build supplémentaire.

```
frontend/
  locales/fr.json      ← référence : toute clé part d'ici
  locales/en.json
  locales/nl.json
  js/i18n-boot.js      ← script classique, bloquant, premier du <head>
  js/i18n.js           ← détection, chargement, t(), formats, hydratation
```

### 1.1 Ordre de chargement — pourquoi deux fichiers

Les scripts applicatifs sont des modules ES (`<script type="module">`), donc
**différés par nature** : ils s'exécutent après l'analyse du document. Si
l'hydratation n'avait lieu que là, l'utilisateur verrait le français écrit dans
le HTML, puis sa langue — un FOUC de traduction sur chaque page.

`js/i18n-boot.js` est donc un **script classique et bloquant**, placé en tête du
`<head>` de chaque page. Il ne fait qu'une chose : masquer le document
(`documentElement.style.visibility = 'hidden'`) et exposer `window.__i18nReveal()`.

Deux contraintes ont dicté cette forme :

* la **CSP est stricte** (helmet + `nginx/snippets/adcraft-security.conf`,
  « aucun handler inline ») : ni `<script>` ni `<style>` inline. On masque donc
  via CSSOM — `element.style.*` n'est pas soumis à `style-src` — et depuis un
  fichier servi par la même origine ;
* **jamais de page blanche**. Trois garde-fous en cascade :
  1. `i18n.js` appelle `__i18nReveal()` dans un `.finally()` : succès, clé
     manquante ou dictionnaire injoignable, la page réapparaît ;
  2. `i18n-boot.js` arme un minuteur de **1 200 ms** qui réaffiche la page même
     si `i18n.js` n'a jamais été évalué (réseau coupé, erreur de parsing) ;
  3. **JavaScript désactivé** : `i18n-boot.js` ne s'exécute pas, rien n'est
     masqué, la page s'affiche en français de référence.

`i18n.js` se termine par un `await` de plus haut niveau :

```js
export const ready = init().finally(() => window.__i18nReveal?.());
await ready;
```

Tout module qui importe `i18n.js` attend donc automatiquement la fin du
chargement du dictionnaire. C'est ce qui permet d'écrire `t()` directement dans
les gabarits en *template literals* (`nav.js`, `tarifs.js`, `components.js`…)
sans propager de promesse ni câbler de garde.

### 1.2 Détection de langue

Par ordre de priorité : **`?lang=` dans l'URL → `localStorage` →
`navigator.languages` → `fr`**.

`localStorage` est écrit dans deux cas, clé `app.lang.v1` :

* sur **choix explicite** de l'utilisateur (`setLang()`) ;
* **à l'arrivée par un lien `?lang=`** (dans `detect()`). C'est voulu : les
  redirections en dur du code (`auth.js` → `/app.html`, `register.js` →
  `/tarifs.html`…) et les `<a href="/…">` ne portent pas `?lang=` ; sans cette
  mémorisation, un visiteur arrivé sur un lien `?lang=nl` retomberait sur
  `navigator.languages` dès le premier clic interne.

La détection par `navigator.languages`, elle, n'écrit jamais rien.

Changer de langue mémorise le choix, aligne `?lang=` sur l'URL courante (pour
rester cohérent avec les `hreflang`) puis **recharge la page**. C'est délibéré :
la moitié de l'interface est régénérée par des gabarits JS (cartes de formules,
lignes d'historique, bandeaux, modales) ; un rechargement les reconstruit tous
sans code de re-rendu à maintenir page par page.

### 1.3 Ce que le HTML contient encore

Le texte français reste **écrit dans le HTML**, avec un attribut `data-i18n`. Ce
n'est pas une duplication : c'est le repli avant hydratation, sans JS, et quand
aucun dictionnaire n'a pu être chargé (`applyDom()` ne fait alors rien, plutôt
que de remplacer chaque libellé par la chaîne vide que renverrait `t()`). Le
dictionnaire fait autorité.

Les deux dictionnaires (français, filet de secours, et langue cible) sont
demandés **en parallèle** et en `cache: 'no-cache'` (revalidation à chaque
chargement, 304 si inchangé : pas de dictionnaire périmé après un déploiement).
Si seule la langue cible échoue, la page passe en français.

Une seule différence volontaire : le HTML statique est **sans nom de marque**
(« Notre outil compose… », `<title>Tarifs</title>`), alors que le dictionnaire
porte `{{brand}}` (« {{brand}} compose… », « Tarifs — {{brand}} »). Ainsi, si le
filet de sécurité des 1 200 ms se déclenche, l'utilisateur lit une phrase
française valide, jamais un `{{brand}}` brut.

## 2. Convention de clés

Notation pointée, **namespace = page ou composant** :

```
common.*     mots partagés (Supprimer, Chargement…, Adresse e-mail)
nav.*        barre de navigation + sélecteur de langue
footer.*     pied de page
meta.*       <title>, description, Open Graph, JSON-LD (un sous-espace par page)
home.* pricing.* studio.* history.* login.* register.* verify.* admin.* legal.*
themes.*     libellés des 7 thèmes (la VALEUR technique ne se traduit jamais)
categories.* libellés des catégories produit (idem)
plans.*      libellés/arguments des formules, par clé de formule
errors.*     messages d'erreur (voir § 6)
ui.* time.* usage.* cookies.* terms.* verifyBanner.*
```

Trois règles :

| Convention | Sens |
|---|---|
| `cle` | texte pur — injecté par `textContent` ou échappé par `escapeHtml()` |
| `cle_html` | **contient du HTML volontaire** (`<strong>`, `<a>`, `<code>`, `<td>`) — injecté tel quel |
| `cle_one` / `cle_other` | forme pluralisée, choisie par `Intl.PluralRules` |

Le suffixe `_html` est la seule marque qui autorise une injection brute. Tout le
reste passe par `escapeHtml()`. Les variables `{{…}}` remplies avec des données
serveur ou utilisateur (adresse e-mail, message d'erreur, nom de fichier)
**doivent être échappées par l'appelant** :

```js
t('verifyBanner.text_html', { email: escapeHtml(user.email) })  // clé _html
escapeHtml(t('nav.logoutTitle', { email: user.email }))          // clé texte
```

### 2.1 Pluriels

Convention retenue : **`cle_one` / `cle_other`**, résolue par
`Intl.PluralRules(localeActive)` dès que la variable `count` est passée.

```js
t('history.failuresCount', { count: 3 })   // « 3 générations échouées »
t('pricing.current.credits', { count: 1 }) // « · 1 crédit en réserve »
```

Pourquoi `Intl.PluralRules` plutôt qu'un `n > 1 ? 's' : ''` : le français met
**0 au singulier** (« 0 génération »), l'anglais et le néerlandais au pluriel
(« 0 generations »). Le test ternaire se trompe donc systématiquement sur zéro,
et la catégorie correcte est déjà dans le moteur du navigateur. Les langues à
plus de deux formes (pl, ru, ar) fonctionneront sans toucher au code : il suffit
d'ajouter `cle_few`, `cle_many`, `cle_zero` au dictionnaire concerné.

### 2.2 Clé manquante

`t()` cherche dans la langue active, retombe sur le **français** et logge un
avertissement en console. Si la clé n'existe nulle part, `t()` renvoie une
**chaîne vide** et logge — jamais la clé brute : un libellé absent se voit à la
relecture, un `pricing.cta.choose` affiché à un client, non.

## 3. Hydratation du DOM

| Attribut | Effet |
|---|---|
| `data-i18n="cle"` | `textContent` |
| `data-i18n-html="cle"` | `innerHTML` (clés `_html`) |
| `data-i18n-attr="placeholder:cle;aria-label:autre.cle"` | `setAttribute`, autant de paires que voulu |
| `data-i18n-ld="cle"` | `<script type="application/ld+json">` : `name`, `inLanguage` et `description` réécrits |

`data-i18n-attr` couvre `placeholder`, `alt`, `title`, `aria-label` et `content`
(balises `<meta>`) — c'est le même mécanisme pour tout attribut.

## 4. Formats localisés

**Aucun formatage à la main.** Tout passe par `Intl`, piloté par la locale
active :

| Helper (`i18n.js`) | Appuie sur | fr-BE | en-GB | nl-BE |
|---|---|---|---|---|
| `money(9.9)` | `Intl.NumberFormat` | `9,90 €` | `€9.90` | `€ 9,90` |
| `money(0.039, 3)` | idem, 3 décimales | `0,039 €` | `€0.039` | `€ 0,039` |
| `n(412)` | `Intl.NumberFormat` | `412` | `412` | `412` |
| `percent(0.03)` | `Intl.NumberFormat` | `3 %` | `3%` | `3%` |
| `date(s, opts)` | `Intl.DateTimeFormat` | `16 octobre 2026` | `16 October 2026` | `16 oktober 2026` |
| `relative(-2, 'hour')` | `Intl.RelativeTimeFormat` | `Il y a 2 h` | `2 hr ago` | `2 uur geleden` |

`date()` transmet ses options telles quelles à `Intl.DateTimeFormat` : les
dates sont affichées dans le fuseau du navigateur, sauf `timeZone` explicite.
Exception volontaire : l'échéance de rétractation (`tarifs.js`, `fmtDeadline`)
est formatée avec `timeZone: 'UTC'`, parce que le serveur la fixe à 23:59:59
UTC du dernier jour — en heure de Bruxelles, elle glisserait au lendemain et
annoncerait un jour que le serveur refuse déjà.

Ce qui a disparu : `toLocaleDateString('fr-BE', …)` en dur et les
`.toFixed(2).replace('.', ',')` de `tarifs.js`, `app.js`, `components.js` et
`admin.js`. Un `replace` ne peut pas savoir que l'anglais écrit `€9.90` symbole
devant et point décimal, ni que le néerlandais insère une espace après le `€`.

`parseServerDate()` centralise la lecture des deux formats qui cohabitent côté
serveur : SQLite `2026-09-13 17:31:29` (UTC, sans fuseau) et ISO écrit par Node.

**Locales :** `fr-BE`, `en-GB`, `nl-BE` — table `LOCALES` en tête de `i18n.js`.
L'anglais utilise `en-GB` et non `en` générique, qui donnait des dates au format
américain (`9/16/26`) et une horloge 12 h, incongrus sur un site belge. Les
montants sont identiques dans les deux variantes (`€9.90`). `og:locale` reste
`en_US` (voir § 9) : seul le `tag` passé à `Intl` a changé.

## 5. Nom du produit — une constante pour les textes du front

Pour tous les **textes affichés par le front**, le nom vient d'une seule ligne :

```js
// frontend/js/i18n.js
export const BRAND = 'AdCraft';   // ← textes du front : renommer ici
```

Ce n'est **pas** la seule chose à changer pour renommer le service : le backend,
le manifeste et plusieurs noms de fichiers portent aussi le nom en dur (tableau
ci-dessous).

Dans les dictionnaires et le HTML, il n'apparaît que sous forme de variable
`{{brand}}`, injectée automatiquement dans chaque appel à `t()`. Contrôle :

```bash
grep -ri adcraft frontend/ --include=*.json --include=*.html
# → aucun résultat autre que le nom de fichier de l'image du logo
```

Les clés de stockage local ont été dé-marquées au passage
(`adcraft.cookieNotice.v1` → `app.cookieNotice.v1`,
`adcraft.billing.v1` → `app.billing.v1`, nouvelle clé `app.lang.v1`).

### Ce qui reste hors du périmètre de cette constante

Le nom reste écrit en dur ailleurs, là où `BRAND` n'est pas lisible (backend,
fichiers servis tels quels, noms de fichiers). Relevé au moment de l'écriture —
refaire un `grep -rni adcraft . --exclude-dir=node_modules` avant tout renommage :

| Fichier | Champ | Effet visible |
|---|---|---|
| `backend/src/mail.js` (~l. 49-62) | objet, texte et HTML de l'e-mail de confirmation | **oui** — reçu par chaque inscrit, en français |
| `backend/src/config.js` (~l. 96) | expéditeur par défaut (`SMTP_FROM`) | **oui** — nom affiché de l'expéditeur, sauf si `SMTP_FROM` est défini |
| `.env.example` | `SMTP_FROM` | **oui** une fois recopié dans `.env` |
| `backend/src/billing/stripe.js` (~l. 13) | `appInfo.name` du client Stripe | non (métadonnée transmise à Stripe) |
| `backend/src/password.js` | liste de mots de passe interdits (`adcraft`, `adcraft2026`) | non — à compléter avec le nouveau nom |
| `frontend/site.webmanifest` | `name`, `short_name` | **oui** — manifeste PWA statique, lu sans exécuter de JS |
| `frontend/img/logo-adcraft.webp` | nom du fichier, référencé par `js/nav.js` et `login`, `register`, `verify`, `50x.html` | le logo lui-même est à refaire ; le nom de fichier n'est pas visible |
| `frontend/css/input.css`, `frontend/tailwind.config.js` | commentaires | non |
| `nginx/snippets/adcraft-*.conf`, `docker-compose.yml`, `nginx/*.conf` | noms de fichiers de configuration | non — renommer est facultatif, et doit être fait partout à la fois |

Un renommage complet = **la constante `BRAND` + les e-mails et l'expéditeur du
backend + le manifeste + le logo** (le reste est cosmétique). `og:site_name`,
`<title>`, la description, les données structurées, la page légale et la modale
CGU suivent automatiquement la constante.

## 6. Messages d'erreur du backend

Le backend est francophone et hors périmètre. Politique appliquée dans
`js/api.js` :

1. **en français**, on garde le message du serveur — plus précis que le nôtre ;
2. **dans les autres langues**, on affiche notre message localisé, choisi par
   `data.code` quand le serveur en fournit un (`errors.code.<CODE>`), sinon par
   le code HTTP (`errors.status.<nnn>`) ;
3. à défaut, `errors.generic`.

Conséquence : un utilisateur néerlandophone voit un message correct mais parfois
moins détaillé que son équivalent francophone. **Le correctif propre est côté
backend** (renvoyer un `code` machine sur chaque erreur, et laisser le front
choisir le texte). Ajouter un nouveau code métier = ajouter une clé
`errors.code.<CODE>` dans les trois dictionnaires.

## 7. Formules d'abonnement

Le backend renvoie `label`, `pitch` et `features` en français
(`backend/src/billing/plans.js`). `tarifs.js` les retraduit via la **clé de
formule** (`free`, `starter`, `pro`, `studio`), stable et indépendante de la
langue, et retombe sur le texte serveur si une clé inconnue apparaît.

Le premier élément de `features` est la ligne de quota, que la carte recompose
elle-même avec le bon pluriel : `plans.<clé>.features` ne contient donc que
**les avantages qui suivent**. Ajouter une formule côté backend sans ajouter sa
clé au dictionnaire n'est pas bloquant (repli français), mais c'est à faire.

## 8. Sélecteur de langue

`<select>` natif (`renderLanguageSwitch()` dans `i18n.js`), monté par `nav.js`
en **desktop** et dans le **menu mobile**, et par `auth.js`, `register.js` et
`verify.js` sur les trois pages sans chrome commun — sinon on ne peut plus
changer de langue en arrivant directement sur `/login.html`.

* libellés **dans leur propre langue** : Français / English / Nederlands ;
* `h-11` (44 px) sous `lg`, `lg:h-8` au-delà : cible tactile respectée ;
* `<select>` natif = navigation clavier gratuite, plus
  `focus-visible:ring-2 focus-visible:ring-primary-container focus-visible:ring-offset-2` ;
* `aria-label` traduit (`nav.language`).

## 9. SEO multilingue

* `hreflang` `fr` / `en` / `nl` / `x-default` en dur dans le `<head>` des trois
  pages publiques (`index`, `tarifs`, `legal`). `fr` et `x-default` pointent
  l'URL nue, `en` et `nl` la même URL avec `?lang=`.
* `link[rel=canonical]` et `og:url` reçoivent `?lang=` au runtime pour les
  langues non par défaut — cohérent avec les `hreflang`.
* `og:locale` prend la locale active (`fr_BE` / `en_US` / `nl_BE`),
  `og:locale:alternate` les deux autres.
* `<html lang>` mis à jour dynamiquement.
* `sitemap.xml` liste les trois URL de chaque page publique avec leurs
  `xhtml:link` alternates.
* `site.webmanifest` : `lang` + `dir`, `name`/`short_name` (voir § 5).

⚠️ **Limite connue** : `og:site_name`, `og:title`, `<title>` et le JSON-LD sont
remplis au runtime. Les crawlers qui exécutent JS (Google) les voient ; les
robots de partage social qui ne l'exécutent pas (Facebook, Slack) lisent le
repli français sans nom de marque. Si le partage social devient critique, la
réponse est une étape de build qui injecte `BRAND` dans les métas — sans
réintroduire le nom dans les sources.

## 10. Ajouter une langue

1. `cp frontend/locales/fr.json frontend/locales/de.json`, puis traduire —
   **sans ajouter, retirer ni renommer une clé**.
2. Ajouter l'entrée dans `LOCALES` (`js/i18n.js`) :
   ```js
   de: { tag: 'de-BE', html: 'de', og: 'de_DE', label: 'Deutsch' },
   ```
   `label` est **toujours écrit dans la langue elle-même**, jamais traduit.
3. Ajouter le `<link rel="alternate" hreflang="de" …>` dans les trois pages
   publiques et les entrées correspondantes dans `sitemap.xml`.
4. Ajouter une `<meta property="og:locale:alternate">` par page publique
   (`i18n.js` les remplit, il lui faut juste autant de balises que de langues
   alternatives).
5. Relancer les vérifications du § 11.

Rien d'autre : le sélecteur, la détection, les `hreflang` runtime et les formats
se déduisent de `LOCALES`.

## 11. Vérifications

Un seul script est versionné, sans dépendance :

```bash
cd frontend && npm run check:i18n   # = node tools/check-i18n.mjs ; code 0 attendu
```

`tools/check-i18n.mjs` est **à brancher en CI**. Il vérifie quatre choses
qu'une relecture humaine rate :

* aucune clé manquante ni orpheline entre `fr`, `en` et `nl` ;
* même type de valeur (chaîne vs liste) et même longueur de liste ;
* **même jeu de variables `{{…}}`** — un `{{count}}` oublié en traduction fait
  disparaître un chiffre à l'écran sans lever d'erreur ;
* aucune clé référencée par le code et absente du dictionnaire (bloquant), et
  aucune clé du dictionnaire que plus personne n'utilise (signalé, non
  bloquant).

Le reste — français résiduel à l'écran, défilement horizontal, contraste,
débordements de texte dans les trois langues à 400 px et en desktop — n'est
pas outillé dans le dépôt : à vérifier à la main dans le navigateur.

## 13. Points demandant une relecture humaine

1. **`legal.html` — priorité absolue.** Les traductions EN et NL des mentions
   légales, de la politique de confidentialité et surtout des **CGU** (§ 4.1 à
   4.8) sont fidèles mais **n'ont pas de valeur juridique validée**. Une CGU mal
   traduite est opposable : à faire relire par un juriste belge avant mise en
   ligne, en particulier les clauses de responsabilité (4.5), de droits d'usage
   des visuels (4.3) et de droit applicable (4.8). Envisager d'indiquer que la
   version française prévaut en cas de divergence — cette mention n'a **pas** été
   ajoutée d'office, c'est une décision de l'éditeur.
2. **Base légale RGPD.** Les formulations « performance of the contract » /
   « uitvoering van de overeenkomst » et « legitimate interest » /
   « gerechtvaardigd belang » reprennent le vocabulaire officiel du RGPD, mais
   le texte source lui-même reste à valider (cf. l’audit RGPD interne, non versionné).
3. **Noms de formules.** `plans.free.label` est traduit (« Découverte » →
   « Starter kit » / « Kennismaking »), tandis que Starter / Pro / Studio restent
   invariables. Si ces noms doivent devenir des noms commerciaux figés dans les
   trois langues, il faut aligner `free` sur le même principe.
4. **Champs `[À COMPLÉTER]`** de `legal.html` : ils sont traduits (`[TO BE
   COMPLETED]`, `[AAN TE VULLEN]`) mais toujours vides. Ils le sont dans les
   trois langues.
5. **Messages d'erreur du backend** (§ 6) : à terme, faire renvoyer un `code`
   machine par le serveur pour supprimer le repli français.
